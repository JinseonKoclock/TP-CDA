# BACK_E05 — Seeding de la base de données

## Objectif

L'objectif de cette étape était de remplir la base de données `gamerchallenge` avec des données fictives afin de pouvoir tester le futur back-end avec un jeu de données suffisamment varié.

Je ne voulais pas encore travailler sur l'API.  
Je voulais d'abord vérifier que ma base de données fonctionnait correctement avec de vraies relations entre les tables.

---

## 1. Préparation des données de test

J'ai préparé un jeu de données contenant :

- 10 utilisateurs ;
- 15 challenges ;
- 30 participations ;
- 40 votes sur les challenges ;
- 60 votes sur les participations.

Les données ne sont volontairement pas réparties de manière uniforme.

Par exemple :

- certains utilisateurs sont plus actifs que d'autres ;
- certains challenges ont plusieurs participations ;
- certains challenges n'ont aucune participation ;
- certaines participations ont beaucoup de votes ;
- certaines participations n'ont aucun vote ;
- un même utilisateur peut participer plusieurs fois au même challenge.

Cela permettra plus tard de tester des situations différentes dans l'API et dans le classement.

---

## 2. Respect des relations entre les tables

À cause des clés étrangères, les données doivent être insérées dans un ordre cohérent :

```text
USER
  ↓
CHALLENGE
  ↓
PARTICIPATION
  ↓
VOTE_CHALLENGE
VOTE_PARTICIPATION
```

Un challenge doit référencer un utilisateur existant.

Une participation doit référencer un utilisateur et un challenge existants.

Un vote doit également référencer les données déjà présentes dans la base.

Le fichier `seed.sql` respecte donc cet ordre d'insertion.

---

## 3. Vérification des règles métier

Avant d'exécuter le fichier, j'ai vérifié que les données respectaient mon MPD :

- les pseudos sont uniques ;
- les emails sont uniques ;
- les titres des challenges sont uniques ;
- les clés étrangères correspondent à des données existantes ;
- un utilisateur peut avoir plusieurs participations pour le même challenge ;
- le couple `(user_id, challenge_id)` ne peut pas être dupliqué dans `vote_challenge` ;
- le couple `(user_id, participation_id)` ne peut pas être dupliqué dans `vote_participation`.

Lors de la préparation du seed, une règle supplémentaire avait été proposée : empêcher un utilisateur de participer à son propre challenge ou de voter pour lui-même.

Je ne l'ai pas conservée car cette règle ne fait actuellement pas partie de mon MPD ni des règles métier que j'ai définies.

Je préfère ne pas ajouter une règle métier qui n'a pas été décidée dans le projet.

---

## 4. Problème identifié avec les IDENTITY

Dans mon MPD, les identifiants sont générés avec :

```sql
id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Cependant, dans le fichier de seed, les ID sont renseignés manuellement.

Par exemple :

```sql
INSERT INTO "user" (id, pseudo, email, password, created_at)
VALUES (...);
```

J'ai choisi de conserver ces ID explicites car les différentes données du seed sont déjà reliées entre elles grâce à ces identifiants.

Par exemple, une participation peut référencer :

```text
user_id = 9
challenge_id = 1
```

Modifier les ID obligerait donc à reconstruire les relations du jeu de données.

Mais j'avais déjà rencontré un problème avec ce fonctionnement : lorsque des ID sont insérés manuellement, la séquence utilisée par l'IDENTITY peut ne pas être synchronisée avec les ID réellement présents dans la table.

PostgreSQL pourrait alors essayer de générer automatiquement un ID qui existe déjà, provoquant une erreur de clé primaire.

---

## 5. Synchronisation des séquences

Pour éviter ce problème, j'ai ajouté à la fin de `seed.sql` :

```sql
-- Synchroniser les séquences après l'insertion des IDs manuels

SELECT setval(pg_get_serial_sequence('"user"', 'id'), MAX(id)) FROM "user";
SELECT setval(pg_get_serial_sequence('challenge', 'id'), MAX(id)) FROM challenge;
SELECT setval(pg_get_serial_sequence('participation', 'id'), MAX(id)) FROM participation;
```

Ces commandes synchronisent la séquence avec le plus grand ID actuellement présent dans chaque table.

Après le seeding :

```text
user          → MAX(id) = 10
challenge     → MAX(id) = 15
participation → MAX(id) = 30
```

Les prochains ID générés automatiquement pourront donc continuer après ces valeurs.

Les tables `vote_challenge` et `vote_participation` n'ont pas besoin de cette opération car elles n'ont pas d'ID auto-incrémenté : leur clé primaire est composée de deux clés étrangères.

---

## 6. Exécution du seed

Depuis le dossier :

```bash
/var/www/html/gamerChallenge/backend/prisma
```

j'ai exécuté :

```bash
psql -U gamerchallenge -d gamerchallenge -f seed.sql
```

Les données ont été insérées dans PostgreSQL.

---

## 7. Vérification du nombre de données

Plutôt que de vérifier manuellement toutes les lignes avec `SELECT *`, j'ai utilisé une seule requête pour compter les données présentes dans chaque table :

```sql
SELECT 'user' AS table_name, COUNT(*) FROM "user"
UNION ALL
SELECT 'challenge', COUNT(*) FROM challenge
UNION ALL
SELECT 'participation', COUNT(*) FROM participation
UNION ALL
SELECT 'vote_challenge', COUNT(*) FROM vote_challenge
UNION ALL
SELECT 'vote_participation', COUNT(*) FROM vote_participation;
```

Résultat :

```text
user                | 10
challenge           | 15
participation       | 30
vote_challenge      | 40
vote_participation  | 60
```

Les quantités correspondent exactement au jeu de données prévu.

---

## 8. Vérification de la séquence

J'ai également vérifié la séquence de la table `"user"` :

```sql
SELECT
  pg_get_serial_sequence('"user"', 'id') AS sequence,
  last_value
FROM user_id_seq;
```

Résultat :

```text
sequence           | last_value
-------------------+-----------
public.user_id_seq | 10
```

La table contient des utilisateurs avec des ID allant de 1 à 10 et la séquence est maintenant positionnée sur 10.

La synchronisation ajoutée dans `seed.sql` a donc bien fonctionné.

---

## Ce que j'ai compris

Le seeding ne consiste pas seulement à ajouter beaucoup de fausses données dans une base.

Il faut aussi respecter :

- les clés étrangères ;
- les contraintes `UNIQUE` ;
- les clés primaires composites ;
- les règles métier ;
- l'ordre d'insertion des données.

J'ai également compris qu'un IDENTITY et les ID réellement présents dans une table peuvent poser problème lorsque les ID sont insérés manuellement.

Dans ce cas, il faut penser à synchroniser la séquence après le seeding afin d'éviter de futurs conflits de clés primaires.
